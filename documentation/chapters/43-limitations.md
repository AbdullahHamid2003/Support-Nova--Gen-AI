# Chapter 43 — Limitations

SupportNova was built so that no single component is trusted on its own: the GenAI Complaint Intelligence Pipeline proposes, the Python Ground-Truth Validation Pipeline checks the proposal against the Complaint Resolution Rule Matrix and the Knowledge Base, and every case the checks cannot confirm goes to a person. That design limits the damage a weakness can do, but it does not remove the weaknesses. This chapter records them as measured on the implemented system, together with what the system already does about each one and what remains open. All figures come from the demo database (617 development complaints and the 154-case unseen holdout evaluation, both run with the real OpenAI `gpt-4.1-mini` model and prompt `complaint_analysis` 1.2.0) and from the reports in `reports/`. Table 43.1 at the end of the chapter summarises the limitations.

## 43.1 GenAI Variability and Model Quality

The quality of Pipeline 1 is bounded by the configured model. On the holdout run (evaluation run #1, `reports/genai_python_comparison/summary.md`) the GenAI key-field accuracy against the expected labels was 79.2 %, and 93 of the 154 cases contained at least one key-field error in the AI answer. The weakest AI fields were the follow-up type (44.1 %), refund eligibility (60.5 %), priority (62.5 %) and urgency (68.4 %). The AI was stronger than the deterministic classifier on category (89.5 % against 75.7 %) and department (92.1 % against 84.9 %), which is why the two pipelines are compared rather than one being replaced by the other (see Chapter 12).

The consequence is a large manual-review workload. The holdout labels expect 51 of the 154 cases (33 %) to need a person; SupportNova sent 130 (84.4 %) to the review queue. On the development dataset 71 % of the analysed complaints went to review against 39 % expected by the labels. The extra reviews are cases in which the model left out a required action, under-rated urgency, chose a different department or missed a mandatory escalation; Python enforced the rule in each of them, which is the intended behaviour, but a reviewer still has to open and approve the case. The verified-without-review rate on the holdout set was therefore only 14.3 %. A stronger model can be selected with `AI_MODEL` without code changes, but no model other than `gpt-4.1-mini` has been measured, so no improvement is claimed.

Generation is not deterministic. The analysis prompt runs at temperature 0.1 and the customer-communication prompt at 0.3, so two runs on the same complaint can produce different wording and occasionally different classifications. The validation pipeline itself is deterministic: for a given AI answer, Rule Matrix version (`ruleset_hash`) and Knowledge Base state it always produces the same checks, score and decision, and the analysis record stores the prompt versions, policy versions and ruleset hash so that a decision can be explained later. Re-running a complaint (`POST /api/v1/complaints/{ref}/reprocess`) creates a new analysis version rather than overwriting the old one.

## 43.2 Dependence on the External GenAI API

Pipeline 1 depends on the availability, latency and behaviour of the OpenAI API. During the recorded runs 31 AI attempts failed (26 connection errors, 4 timeouts and 1 invalid output); every one was recovered by the controlled retry policy in `backend/src/supportnova/genai_pipeline/`, and all 780 recorded analyses completed with real AI output. When the provider is unreachable after the retries, or no key is configured, the stage is recorded as failed or `not_configured`, no AI output is fabricated, and the complaint is placed in manual review (tested by `tests/backend/integration/test_ai_not_configured.py::test_no_api_key_means_no_ai_output_and_manual_review`). This protects correctness but not throughput: during an API outage the system keeps accepting complaints and running the deterministic checks, while all AI-dependent work waits for people. Provider changes to model behaviour or to the structured-output interface can also break the adapters; the adapter tests in `tests/backend/unit/test_genai_providers.py` run against fake vendor servers and will not detect a change made by the real vendor.

## 43.3 Latency Against the 20-Second Target

The SRS asks for an initial validated recommendation within 20 seconds under normal API and network conditions (NFR 1). The measured full pipeline on the development dataset, processed four complaints in parallel, took p50 21.7 s and p95 33.9 s, and only 32.4 % of complaints completed every stage within 20 seconds; the holdout run gave p50 21.2 s and p95 33.8 s. The time is dominated by the two GenAI calls: the structured analysis averaged 16.5 s and the customer-response call 5.6 s, while retrieval and the 52 Python checks take milliseconds. The stage timings stored with each analysis show that the validated recommendation — preprocessing, retrieval, AI analysis and validation — is ready at p50 16.2 s (mean 17.2 s, p95 24.9 s), and for 80.8 % of the 599 development analyses within 20 seconds. It is, however, saved together with the response draft, so the recorded completion time includes both calls. The target is therefore not met at the median for the full pipeline, and this report does not claim that it is. Chapter 35 gives the per-stage measurements; the options for closing the gap are listed in Chapter 44.

## 43.4 Scalability Has Not Been Load-Tested

NFR 2 asks for support of at least 10,000 complaints, 100 categories and subcategories and 1,000 knowledge-base documents without a redesign. The design is prepared for that scale: the taxonomy, departments and rules are database records rather than code (a new category is added without code changes, `tests/backend/integration/test_defects_and_live_changes.py::test_new_category_without_code_changes`), the complaint table carries composite indexes for the dashboard and queue queries, and retrieval is restricted to active, effective, non-quarantined chunks. The measured system, however, holds about 800 complaints, 46 categories and subcategories (11 + 35) and 24 documents with 29 versions and 484 chunks. No load test at the NFR volumes has been run. Background processing uses an in-process thread pool (`BACKGROUND_WORKERS` = 2, `BATCH_WORKERS` = 4) instead of an external queue, the request rate limiter (`backend/src/supportnova/api/middleware.py`) keeps its counters in the memory of one process, and the retrieval index is an in-memory snapshot of all active chunks (`knowledge_base/store.py`) rebuilt in each application process whenever the Knowledge Base changes. These choices are adequate for a single-instance deployment and the competition evaluation; running several application instances would need a shared queue and a shared rate-limit store (see Chapter 44).

## 43.5 Retrieval Quality

Retrieval is hybrid: BM25 over chunk text, vector search with the default local feature-hashing embedder (`backend/src/supportnova/knowledge_base/embeddings.py`), rule-guided expansion with the sections the Rule Matrix cites for the candidate subcategories, and reciprocal-rank fusion with a document-type precedence tie-break (`knowledge_base/retriever.py`). The local embedder is deterministic and needs no model download or key, but it is a classic information-retrieval technique, not a neural embedding model, so it matches vocabulary rather than meaning. An external embedding provider can be configured (`EMBEDDING_PROVIDER`), but it has not been evaluated.

The live runs exposed the practical effect. The routing policy RTE-RUL-14 was retrieved for only 6 % of complaints, and routing was the most frequent critical mismatch; prompt 1.2.0 therefore supplies RTE-RUL-14 sections 3–5 and SLA-RUL-15 section 5 as fixed reference data instead of relying on retrieval (Chapter 22). Citation precision also remains weak: on the holdout set the AI's set of policy references matched the expected set exactly in only 5.9 % of cases, against 76.3 % for the Python decision, because the model tends to cite neighbouring or additional sections. The validation checks limit the harm (POL-002 rejects outdated versions, POL-003 requires cited policies to be in the case evidence, POL-004 reports required policies that were not cited, HAL-004 rejects invented policy IDs), but a correct policy that retrieval did not surface cannot be cited by the AI.

## 43.6 Quality and Completeness of Policies and Rules

The Rule Matrix is the ground truth, so its errors become the system's errors. If a rule, parameter or routing entry is wrong, Python will enforce the wrong outcome consistently and will flag a correct AI answer as a mismatch. The integrity checks (`tests/backend/unit/test_rule_engine.py::test_rule_matrix_integrity`), the rule simulator and the edit preview (`POST /api/v1/rules/validate`, `POST /api/v1/rules/simulate`) catch structural errors such as unknown actions, departments or policy references, but they cannot judge whether a rule reflects the organisation's intent.

The expected labels of the dataset share this dependence. They are produced by applying the Rule Matrix to the facts each scenario declares (`docs/dataset.md`, section 2), so the evaluation measures how well each pipeline recovers the policy-correct outcome from raw text; it does not measure whether the Rule Matrix itself is the right policy. The dataset and the Knowledge Base are synthetic and describe the fictional Lumora Home Technologies, so results on real complaints and real policies may differ.

Some urgency levels in the Rule Matrix do not match the wording of the urgency policy that the model reads. The rules treat any personal-data exposure (PRV-BRC) as Critical, while SLA-RUL-15 section 5 lists "privacy exposure" under High, and a marketing-consent complaint (PRV-CON) is Medium in the rules. The model follows the text, Python enforces the rule, and the case is reviewed. Publishing an SLA-RUL-15 version that states the rule-matrix levels would remove these mismatches; it has not been done, so the mismatch is documented rather than hidden.

The deterministic classifier that selects which rules apply is also imperfect. On the holdout set its category accuracy was 75.7 % and its subcategory accuracy 68.4 %. When its confidence is low, the AI category is used provisionally and the case is held for a reviewer, whose decision is final. Every complaint that falls outside the 35 subcategories triggers REV-013 and is reviewed; it is not resolved automatically.

## 43.7 Context and Input Limits

Each analysis call sends about 9,500 input tokens: the reference data (taxonomy, departments, action catalog, escalation levels, urgency and routing policy, follow-up types), the top retrieved evidence (`RETRIEVAL_TOP_K` = 10), policy conflicts, verified facts and the complaint. The output is capped at 6,000 tokens for the analysis and 2,500 for the customer communication. Complaint input is bounded by the API (title 200 characters, description 10,000 characters, supporting information 6,000 characters; `backend/src/supportnova/api/v1/complaints.py`). Very long complaints, long attachment text or a Knowledge Base that grows far beyond its current size will compete for the same context, and the model may give less attention to evidence placed later in the prompt. Attachments are stored and hashed, and the model receives only their file names and content types (an image attachment counts as photo evidence for the rules); the contents of an attachment are not analysed.

## 43.8 False Positives and False Negatives of the Safety Nets

The safety nets are strong on the measured data but not perfect, and the numbers show where they miss. On the holdout set, 93 AI answers had at least one of the six key fields (category, subcategory, department, urgency, priority, escalation level) wrong; in 92 of them (98.9 %) the rules supplied the correct value or the case went to manual review, so in one case the error was neither corrected nor reviewed. Of the 51 cases the labels expect to be reviewed, 48 were sent to review (recall 94.1 %), so three were verified without a person. Prompt-injection screening detected all 6 holdout injections with no false positives, and the 18 adversarial lab scenarios were all caught (Chapter 34), but the screener in `backend/src/supportnova/security/injection.py` is pattern-based: a paraphrased, translated or otherwise novel attack may not match, and unusual but benign wording can be flagged. Signal detection for safety, security and legal risk is lexical with negation handling, so it can miss a risk described in unexpected words and, in rare cases, react to a risk word used in another sense; the dataset contains 14 deliberate lexical traps for this reason. Duplicate and repeat detection depends on thresholds (`NEAR_DUPLICATE_THRESHOLD` = 0.86, `REPEAT_SIMILARITY_THRESHOLD` = 0.30, `DUPLICATE_WINDOW_HOURS` = 24); the holdout duplicates (2/2) and repeats (4/4) were all found, but other data could produce missed or spurious links. These measurements come from 154 holdout cases, so the confidence intervals are wide.

## 43.9 Limits of Unsupported-Claim Detection

Hallucination checks (`backend/src/supportnova/hallucination_checks/grounding.py`) verify that the important facts in the AI output — reference numbers, amounts, policy IDs, products, dates and extracted entities — can be traced to the complaint, the evidence or the Rule Matrix. The unsupported-promise checks (`hallucination_checks/promises.py`) look for refund and compensation promises, guarantees, unsupported timelines and amounts and unauthorised exceptions, always judged against the Python-validated decision. Both are lexical: they tolerate paraphrase of narration but cannot understand the full meaning of a sentence. A subtly misleading statement that uses no checked amount, timeline, reference or promise wording can pass. This is why safety and privacy complaints, and cases with legal-threat, staff-harassment, injury or smart-lock security signals, always require human approval (REV-008 in `rules/complaint_rules/review_rules.yaml`), and why a customer response is recorded as sent only when a user with the `complaint:respond` permission releases it (`POST /api/v1/complaints/{ref}/responses/{response_id}/send`).

## 43.10 Cost

Every complaint costs two GenAI calls, and failed attempts cost more. On the recorded runs an analysis call used on average about 9,500 input and 1,390 output tokens and a communication call about 1,640 input and 310 output tokens, which is roughly 11,300 input and 1,730 output tokens per completed complaint including retries (`ai_runs` table). Cost therefore grows linearly with complaint volume, with re-processing and with evaluation runs, and it rises further if a larger model is selected. The application records the tokens of every call but does not convert them to a currency amount or enforce a budget, because prices depend on the provider's current price list.

## 43.11 Security Considerations

Chapters 24 and 34 describe the controls that are implemented and tested: bcrypt password hashing, JWT sessions in HttpOnly cookies with a CSRF header, account lockout, server-side RBAC on every endpoint, security headers, upload validation, PII redaction, injection screening and an append-only, hash-chained audit log. Some limits remain. There is no multi-factor authentication. The demonstration accounts share one configurable password (`DEMO_PASSWORD`) and must be disabled or changed outside an evaluation (`SEED_DEMO_USERS`). The embedded development database uses a local default password and listens only on 127.0.0.1; a real deployment must use managed credentials. The append-only rule of the audit log is enforced by a PostgreSQL trigger, so a database superuser could still disable it; the hash chain makes such tampering detectable (`GET /api/v1/audit/verify`) but cannot prevent it. Uploaded documents are checked for type, size, signature and instruction-bearing content, but they are not scanned by an antivirus engine. Before complaint text is sent to the AI provider, `backend/src/supportnova/security/pii.py` redacts payment-card numbers (Luhn-checked), security codes, passwords, one-time codes, e-mail addresses and phone numbers; customer names, addresses and the narrative of the complaint are still sent, because the analysis needs them, so the provider's data-handling terms apply to that content. Redaction is pattern-based and can miss sensitive data written in an unusual format.

## 43.12 Simulated Integrations and Deployment Status

Direct integration with CRM, payment, call-centre or Zendesk systems is outside the mandatory SRS scope (section 1.4), and SupportNova does not provide it. Customer responses are drafted, validated, approved and recorded inside the application; delivery through the customer's preferred channel is simulated and labelled as such in the timeline, since there is no email or SMS gateway. Order and eligibility facts come from a simulated order ledger (`backend/src/supportnova/complaint_processing/order_facts.py`). At the time of writing the application runs locally and through Docker Compose; the Render blueprint (`render.yaml`) is prepared but no public deployment URL exists yet, so the 99 % uptime requirement (NFR 5) has not been measured. These points are also listed with the other open submission items in the Documentation and Implementation Gaps list (Appendix O).
